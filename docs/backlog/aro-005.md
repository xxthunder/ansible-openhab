# [ARO-005] Settle the tagging and release policy

**Status**: Open
**Priority**: Low
**Component**: `AGENTS.md`, git tags
**Related**: [ARO-002](aro-002.md) — cuts `v1.0.0-rc1`, this repo's first tag
ever.

**Summary**:
As the role maintainer, I want an explicit versioning policy, so that consumers
can tell a breaking change from a safe bump without reading the diff.

**Description**:
The repo was untagged until [ARO-002](aro-002.md). `AGENTS.md` documents the
RC-first *process* but not the *numbering*, and ARO-002 is already a breaking
change — `openhab_repo` is removed and now fails the run — which under semver
would be a major bump, except there is no previous version to be major relative
to.

Starting at `v1.0.0` is the obvious reading given the lineage decision: the
`xxthunder` copy has its own release line, so its first release is 1.0.0 and
future breaking changes go to 2.0.0. That should be written down rather than
inferred, along with what counts as breaking for an Ansible role — removing or
renaming a variable, changing a default, changing the shape of a task's effect
on the target.

**Acceptance Criteria**:
- [ ] `AGENTS.md` states the versioning scheme and what counts as a breaking
      change for this role.
- [ ] The policy says how a consumer learns about a breaking change — release
      notes, `README.md` upgrade section, or both.
- [ ] Existing tags are consistent with the stated policy.

**Out of scope**:
- Automating releases.
